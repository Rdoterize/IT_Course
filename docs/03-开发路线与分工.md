# 某专业师生业绩管理系统——开发路线与分工

日期：2026 年 10 月 17 日。用户已选择 Java + Vue，并以尽快完成为目标。下面的 8 人分工是课程小组的建议安排；姓名、实际投入和完成情况由小组如实补充，不把 AI 代理当作真实组员。

## 1. 交付策略

优先完成单条可验收业务链，再补齐分类、图表和报告。统一 API、枚举、权限和统计口径，前后端并行开发；使用 H2 免安装演示，保留 MySQL 部署路线。

阶段按依赖顺序推进，不以未经评估的日历承诺代替验收。任何压缩工期都不省略越权、状态流转和统计去重的检查。

| 阶段 | 主要工作 | 结束标准 |
| --- | --- | --- |
| A：需求固定 | 确定首版范围、角色、成果字段、状态、统计口径；冻结接口契约 | 能根据一条竞赛成果说明从录入到导出的全过程 |
| B：基础架构 | 建立数据库、登录、数据权限和前端布局 | 三种角色可登录，未授权数据不能访问 |
| C：业务闭环 | 成果、参与指导、材料、审核、导出 | 一项成果可完整流转并在导出包中追溯 |
| D：范围补齐 | 八类成果、指标、图表、账号维护、筛选 | 各入口与后端真实数据联通 |
| E：集成交付 | 构建、业务测试、浏览器检查、MySQL 验证、文档 | 问题关闭或列明限制，保存真实验证记录 |

## 2. 8 人职责建议

| 成员 | 主责 | 主要交付 | 交叉检查 |
| --- | --- | --- | --- |
| 1：组长 | 需求与总体协调 | 需求规格、接口约定、合并集成、报告统稿 | 与 8 检查验收清单 |
| 2 | 认证与权限后端 | 登录、密码、用户管理、数据范围 | 与 5 检查会话和权限页面 |
| 3 | 成果后端与数据库 | 主表、分类详情、参与/指导关系、筛选 | 与 6 检查字段和编辑状态 |
| 4 | 审核与指标后端 | 状态流转、自审限制、审核记录、指标 | 与 6 检查退回再提交 |
| 5 | 前端基础与账号 | 布局、导航、登录、用户管理、密码 | 与 2 检查角色差异 |
| 6 | 前端成果与审核 | 列表、表单、详情、材料、审核界面 | 与 3、4 联调业务 |
| 7 | 统计和导出 | 统计口径、图表、Excel 与材料索引 | 与 3 核对多人去重 |
| 8 | 材料、部署与测试组织 | 私有存储、运行脚本、部署、测试汇总 | 与 1 检查报告与实际一致 |

每人负责自己模块的设计、实现说明和验证记录。组长负责整理，不能代写全部成员工作；代码评审和测试应覆盖其他成员模块。

## 3. 协作规范

1. 接口变更先更新 `CONTRACT.md`，注明受影响页面和测试。
2. 每次变更围绕一个可说明的业务行为，避免多人同时修改同一基础文件。
3. 不提交真实师生隐私、密码、运行数据库、上传材料和依赖目录。
4. 提交前完成本模块验证；合并后运行统一构建及业务流程检查。
5. 修改口径后同步更新报表、材料索引、需求、用户手册和测试预期。

建议答辩顺序：问题背景 → 技术选择 → 多人一成果模型 → 三角色权限 → 录入审核演示 → 统计及材料包 → 验证与不足。
